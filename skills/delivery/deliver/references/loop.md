# Loop: a fresh session per PBI

```powershell
pwsh <skill-dir>/scripts/Invoke-DeliverLoop.ps1 -Milestone M004 -Max 5
pwsh <skill-dir>/scripts/Invoke-DeliverLoop.ps1 -Target 860,870 -Model opus
```

Or with the shell command `deliver-loop` (`skills-manage` offers it after the `delivery` group): `deliver-loop -Milestone M004 -Max 5`. It resolves the installed script (project, `~/.claude/skills`, `~/.agents/skills`), passes all arguments through and exits 1 with a message when none is installed. In herdr (`HERDR_ENV=1`) it starts the loop in its own workspace `<repo> · deliver` (tab `deliver-loop`, `scripts/Start-LoopWorkspace.ps1`), because the herdr sidebar shows one state per workspace by the selected tab; outside herdr it runs in the current terminal.

## Model per PBI (tier)

Without `-Model`, each iteration takes the model of the picked PBI's tier (`references/roles.md`): `Tier:` line of the body (`fast` haiku, `standard` sonnet, `strong` opus), else its size (S fast, M standard, L strong), else standard (sonnet). The loop logs it before the iteration, e.g. `#51 tier fast (Tier line) → model haiku`, and records the model in `progress.jsonl` (`iteration-start`). One REST read of the PBI body per iteration. `-Model <name>` passes that model for every PBI instead. With `-Harness copilot` the default stays `auto`.

`-Milestone` takes `M<nnn>` (legacy: the title): the `github-milestone` lookup (`Get-Milestones.ps1 -Mode issues -Name <name>`) resolves `M004` to the title `M004` or, after `/github-milestone close`, `M004 (0.2.0)` (also `M004 Topic`), and the loop passes `--milestone M004` unchanged, so a run started before the rename keeps working after it. The release-review state file `release-review-<key>.json` (`references/release-review.md`) is keyed by the unpadded `M<n>` (`M003` → `M3`, one file for both forms).

Run `Invoke-DeliverLoop.ps1` from the repository root; the shim `deliver-loop` does that itself from any directory of the repository (it changes to the git toplevel, so state, logs and the herdr workspace are the same everywhere; outside a git repository it keeps the current directory). It starts `claude -p "/deliver <nr> --unattended --max 1" --model <model> --permission-mode auto --output-format stream-json --verbose` once per PBI (`--model` per PBI by tier unless `-Model` overrides it; `-Harness claude` is the default). The allowlist is `references/permissions.md`; the script checks nothing more.

## Harness

| `-Harness`         | Command per PBI                                                                                                                                                                       |
| :----------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `claude` (default) | `claude -p "/deliver <nr> --unattended --max 1" --model <model> --permission-mode auto --output-format stream-json --verbose`                                                         |
| `copilot`          | `copilot -p "/deliver <nr> --unattended --max 1" --model <model> --allow-all-tools --allow-all-paths --allow-all-urls --no-ask-user --output-format json` (JSONL, one event per line) |

Any other value fails with exit 64 and the list of supported harnesses before the first iteration. Stop rules and exit codes read GitHub only and are the same for both. `-Model` is passed as given. Without `-Model`, `-Harness copilot` uses `auto` (Copilot picks the model of the plan); `sonnet` is a Claude name and Copilot rejects an unavailable `--model` with exit 1 (`Model "x" from --model flag is not available`), so pass a Copilot model of your plan only when you want a fixed one. Wait ceiling (#461): `-p` stops background tasks (subagents) 10 minutes after the last turn of the session. The loop sets `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0` (wait indefinitely; `-Harness claude`) or `COPILOT_TASK_WAIT_TIMEOUT_SECONDS=3600` (`-Harness copilot`) for each iteration when the variable is unset in its environment; a value you set is passed unchanged, and the variable is restored after the iteration. When the stderr of an iteration reports `Background tasks still running … stopping them` and the PBI set did not change, the end line reads `no progress: a subagent was stopped by the wait ceiling (<VAR>=<value>)`; result and exit code stay `no progress` / 1.

Copilot's JSONL (verified live against Copilot CLI 1.0.105, recorded in `test/skills/delivery/fixtures/copilot-cli-1.0.105.jsonl`) feeds the step log, the colored log and the notifications from `tool.execution_start` (`data.toolName`, `data.arguments`: tool step), `assistant.message` (`data.content`: text and the `#<nr> <step>: <result>` progress lines; empty while the message only carries `toolRequests`) and `tool.execution_complete` with `success: false` (`data.error.message`: `✗`). Subagents: `subagent.started` (`data.toolCallId`, `data.agentDisplayName`) names the subagent, and every event of its tools carries `data.parentToolCallId` of that call, so steps get the prefix `[<agentDisplayName>]`. The final `result` event carries `exitCode`. Other event types (deltas, reasoning, usage) are written to the jsonl, not to the log. Unverified: the format of other Copilot versions, and events of a `/deliver` run itself (the fixture is a small tool/subagent session).

Permissions on a live `-p` run: `--allow-all-tools` alone denies file access outside the cwd (`view /tmp/…` fails with `Permission denied because no interactive user response was available`, also inside subagents), and URLs in shell commands are denied the same way. The loop therefore passes `--allow-all-tools --allow-all-paths --allow-all-urls` (what `--allow-all` / `--yolo` combine), so subagent worktrees and `gh`/`curl` URLs work. This replaces the per-tool allowlist of `references/permissions.md`.

## Loop or one session

- `--inline` or a few PBIs (up to `deliver.loopThreshold`, default 3): one `/deliver` session delivers them, you watch, questions are welcome.
- Interactive `/deliver --milestone` (or a Feature or Epic with more PBIs): the session starts the loop and stays a thin control session (`references/control.md`). It prints the progress and the status block between PBIs, brings `needs-decision` PBIs to you, delivers `interactive` PBIs itself and runs the release step once after the loop ends `done`. When its own context passes `deliver.controlContextTokens` (default 200000) it prints the status block and the resume command and stops.
- The loop alone (`deliver-loop`): a whole release or a Feature overnight, unattended. Each PBI starts with an empty context, a dead session (sleep, crash, rate limit) costs one PBI, and `deliver` keeps all state in GitHub, so there is no queue file.

## Stop rules

Checked from GitHub (not from the output) before and after each iteration, on the open PBIs of the targets without `needs-decision` / `needs-refinement` / `interactive` (unattended, `deliver` skips `interactive` PBIs; they count as held):

An open `release-test` issue is not part of that set (also when passed explicitly as a Target: `Invoke-DeliverLoop.ps1` drops it from the targets): as the last open item it neither keeps the loop from `done` nor makes it `blocked`. `Get-DeliverStatus.ps1` counts it in `total`, as waiting (`release test`, or `release test, waits for <n> open items`) and, once an RC is posted on it (comment marker `<!-- release-test-rc -->`), as needs you `RC test <issue URL>`.

Between the rounds two rules run (`ObjectiveLoop.ps1`, before the stop check; `-DryRun` only prints them):

- **contract-change**: a merged PR since the start of the last round whose closed PBI (`Closes #<nr>` in its body) carries `contract-change`, set by `deliver` step 6 on the PBI issue (a label on the PR counts too) (in any repository of the objective; each PR once per run) sets `needs-refinement` and a comment with the PR link on every open child downstream of it: the children of a repository that has a `Requires:` line on the PR's repository, and the children whose `blocked-by` list holds an issue the PR closes (`Closes #<nr>` in its body). A child that already waits on `needs-refinement`, `needs-decision` or `release-test` is left alone. The next round then skips them (`planner refine <nr>` lifts the pause by hand).
- **rc edge**: an unmet `Requires: <repo>@<M> rc` on a milestone that has a `release-test` issue and no open `pbi` or `bug` besides it runs `/deliver --milestone <M> --unattended --max 1` once per run in the checkout of that upstream repository (the harness of the loop, `-Model` or sonnet). The session reaches step 9 and posts the RC; the release PR into `main` stays the human gate (deliver never merges it), and the edge is met once the RC marker is posted.

These two rules and the repositories' own loops are the only writes of the mode (labels and comments through `gh api -X POST`); it still never closes the objective.

| Result      | When                                                                                        | Exit |
| :---------- | :------------------------------------------------------------------------------------------ | :--- |
| done        | no open PBI left (a `merging` PBI, auto-merge on, is handed to GitHub and no longer counts) | 0    |
| max reached | `-Max` iterations ran (delivered, blocked or paused PBIs in total)                          | 0    |
| blocked     | open PBIs remain, all wait on an open blocker or a label                                    | 2    |
| no progress | the set did not change after an iteration; prints the last log lines, never retries         | 1    |
| stopped     | the stop file of the run exists before an iteration                                         | 0    |

## Objective: rounds over repositories

```powershell
pwsh <skill-dir>/scripts/Invoke-DeliverLoop.ps1 -Objective GravionLabs/telos#12 -Max 5
deliver-loop -Objective GravionLabs/telos#12 -DryRun
```

`-Objective <owner>/<repo>#<nr>` (an `[Objective]`, `github-issue` `references/objectives.md`; not combined with `-Target` or `-Milestone`, no shim of its own) runs rounds from the checkout of the objective's repository. A round reads `scripts/Get-ObjectiveStatus.ps1` (REST GET only) and starts, one repository after the other (or several at once, `deliver.parallel` below), in every repository with state `ready` its own loop `Invoke-DeliverLoop.ps1 -Target <open sub-issues of the objective in that repository> [-Max <k>]` (no direct sub-issue there: its ready PBIs and Bugs) in the checkout of that repository, with the same `-Harness` and `-Model`; then it reads the state again. `-Max <k>` is passed to each repository's loop per round. Before each repository's loop it writes `.agents/deliver-loop/context.md` in that checkout when a repository it `Requires:` merged PRs since its last green loop (first round: 7 days): link, title, diff stat; passed as `-Context` and so as `--context` to `/deliver`, where step 5 gives it to the fix subagent as fenced data. `deliver-loop -Context <file>` does the same for a hand-made file; a missing file leaves the prompt unchanged. `deliver.parallel` in the objective checkout's `.agents/config.json` (integer ≥ 1, default 1; an invalid value warns and counts as 1) is how many repository loops a round runs at the same time: with `n > 1` up to `n` ready repositories start together (preflight and context file first, one after the other), at most one loop per repository, their output prefixed `[<repo>]`; the round waits for all of them, and the heartbeat stop and `release` reach every running checkout. Within a repository delivery stays sequential, and every PBI is claimed by `deliver` as before (`references/claim.md`). After the loops each round prints `round <n> results: <repo> done|blocked|no progress|failed (<code>), …` and logs its API usage `round <n> api: rest +<calls>, graphql +<calls> (remaining …)` from `gh api rate_limit` before and after the round (all processes of the token; `n/a` when the read fails or the hourly window reset). The state comes from GitHub only, so an aborted round resumes with the same command. The mode never closes the objective; closing it after the acceptance criteria is yours.

Checkout of `<owner>/<repo>`: the objective's own repository is the current checkout; else the entry of `~/.config/deliver/checkouts.json` (`{ "<owner/repo>": "<path>" }`, cloned there when the path is missing); else the sibling folder `<root>/<repo>` of the current checkout (its `origin` must be `<owner>/<repo>`); else a fresh `gh repo clone` into `~/.cache/deliver/checkouts/<owner>/<repo>` (reused by later runs). Before each repository's loop the preflight runs in that checkout (`Test-DeliverPreflight.ps1 -Unattended -Text -Check skills,allowlist,worktrees`, its own allowlist; unattended: lines printed, the run goes on); `-NoPreflight` skips it.

Runner: an objective runs on exactly one runner (`scripts/ObjectiveRunner.ps1`). At the start the loop sets the runner marker on the objective (`github-issue` `references/objectives.md`, "Runner marker": one comment, replaced in place, never a second one; host `DELIVER_RUNNER_HOST`, else the machine name); a foreign live marker ends the run `handed over` before any repository, a dead one (heartbeat older than 30 minutes) is taken over (`runner: <host> took over the dead marker of <other>`). A heartbeat thread refreshes the marker every 10 minutes (`DELIVER_OBJECTIVE_HEARTBEAT_SECONDS`), also while a repository loop runs; when it finds a foreign host it writes the stop file of the running repository loop, so that loop ends after its running PBI. Before every round and every repository the loop checks the marker: a foreign host ends the run `handed over`. Handover happens only at these boundaries. The marker stays after the run; its heartbeat ages, so after 30 minutes another host starts without a takeover. A second objective loop of the same objective on the same host ends `handed over` at once (`~/.cache/deliver/objectives/<owner>/<repo>/<nr>/running.json`).

```powershell
deliver-loop takeover GravionLabs/telos#12 [-Force]
deliver-loop release GravionLabs/telos#12
```

`takeover` (`scripts/Set-ObjectiveRunner.ps1`) sets the marker to this host: without asking when it is missing, own or dead, a foreign live one only with `-Force` (else exit 1, nothing written); the old runner hands over at its next heartbeat or boundary, then start `deliver-loop -Objective` here. `release` on the runner's host: with a running objective loop it writes the release request and the stop file of the running repository loop; at the boundary the loop pushes every local branch with commits on no remote (not `main`, `master`, `release/*`) in the checkouts of the run, posts a status comment (the `Get-ObjectiveStatus.ps1 -Text` block), deletes the marker and ends `released`. Without a running loop `release` does that itself (own marker only, a foreign one: exit 1).

`-DryRun` prints for the first round which repositories would be started with which targets and checkouts (`round 1: <repo> would start deliver-loop -Target <nr…> in <path> (<sibling, checkouts.json, clone, current>)`) and starts, clones and checks nothing.

| Result      | When                                                                                                                                                                                                                               | Exit |
| :---------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :--- |
| done        | the objective is closed                                                                                                                                                                                                            | 0    |
| gated       | no repository is ready and every open one waits only on a gate (an unmet `Requires:` line, only `release-test` items open) or all are done; prints `needs you:` with the gates (release PR, RC test, release, acceptance criteria) | 3    |
| blocked     | no repository is ready and one waits on something else (blocker, `needs-decision`, `needs-refinement`, no PBI yet)                                                                                                                 | 2    |
| no progress | a round left the objective state (per repository status, open/closed counts, ready items, gates) unchanged                                                                                                                         | 1    |
| handed over | a foreign live runner marker at the start or at a round boundary                                                                                                                                                                   | 4    |
| released    | `deliver-loop release` during the run: branches pushed, status comment posted, marker deleted                                                                                                                                      | 0    |
| dry run     | `-DryRun`                                                                                                                                                                                                                          | 0    |

## Stop a run

The file `.agents/deliver-loop/<run>/stop` (any content) asks the loop to stop. It is checked before every iteration, also the first. Seen during an iteration, the loop sends one `attention` event `stopping` (`stops after #<nr>`, step line `stop requested: stops after #<nr>`, tone neutral), lets that iteration end and starts no further one. The result is `stopped`: exit 0, `run.finished` with `stopped`, a `result` record, the notification `loop result: stopped`, the stop file deleted, and a last line `resume: deliver-loop <the same arguments>` (`-Max` reduced by the iterations run). `deliver-loop stop [--now] [--cancel]` (from any directory of the repository) runs `scripts/Request-LoopStop.ps1 [-Now] [-Cancel] [-Run <id>]`: it takes the run of `.agents/deliver-loop/latest.txt` when its `progress.jsonl` has no `result` record, writes the stop file (empty, `now` with `--now`) or deletes it with `--cancel`, and prints one line; no running loop: exit 1 and nothing written. With `now` the `/deliver` session also starts no further step: the loop exports `DELIVER_LOOP_DIR` (the `.agents/deliver-loop` directory) to the harness, `Report-Progress.ps1 -Type step.finished` prints `STOP requested` when `<run>/stop` contains `now`, and the session releases its claim, keeps branch and PR, reports `issue.finished -Outcome skipped -Reason "stop requested"` and ends. The loop then ends `stopped` (an unchanged PBI set is not `no progress`); `/deliver <nr>` continues the PBI. A running subagent or `gh pr checks --watch` is not interrupted.

## Observability

- `.agents/deliver-loop/<run>/progress.jsonl` (`<run>` is the run id of the events below): one record per `start`, `iteration-start`, `iteration-end` and `result` for a control session; `.agents/deliver-loop/latest.txt` holds the path of the newest run.
- `.agents/deliver-loop/<run>/<nr>.jsonl`: every stream record as it arrives (git-ignored). `<nr>` is the first ready PBI at the start of the iteration; the loop starts the session with exactly that number (`/deliver <nr> --unattended --max 1`), so file name, `iteration-*` records, `issue.started` and the tier model all name the PBI the session delivers.
- Outcome `merging` (`issue.finished -Outcome merging`, written as `deliver.merging`; auto-merge on, the issue stays open until GitHub merges): counts as progress, the loop does not select the PBI again, the status block shows it as waiting (`Get-DeliverStatus.ps1 -Merging`), the progress reducer as neither delivered nor blocked (`deliver.merging[]`, its task stays open until `delivered`).
- A PBI whose only open blockers are `merging` PBIs waits: the loop prints `#<nr> select: waits for merge of #<blocker>` and polls `scripts/Get-MergingPrs.ps1` (REST, every 60 s at most) instead of `blocked` or `no progress` (`references/merging.md`).
- `.agents/deliver-loop.log` (plain) and stdout (colored when stdout is a terminal and neither `-NoColor` nor `NO_COLOR` is set, else plain): the tool lines `HH:MM:SS <tool> <description or file>` and tool errors with `✗` come from the stream; short assistant text is logged uncolored (`»`) and never parsed. The step lines `HH:MM:SS #<nr> <step>: <result>` come from the events: while the harness runs, the loop follows the run's event file and prints every new `step.finished`, `attention` (`<kind>: <reason>`) and `issue.finished` (`<outcome>: <reason>`) event, so a step exists only when the harness reported it through `Report-Progress.ps1`. Subagent steps carry the agent description as prefix (`[Review PBI #401 diff] Bash …`). Long text is cut to the terminal width (minus 40 for time, prefix and tool, at least 120), to 120 characters when stdout is redirected.
- Colors of stdout on a terminal (time dim, tool name cyan, `✗` and tool errors red). A step line is colored by the `tone` of its event: `success` green, `info` cyan, `warning` yellow, `danger` red, `neutral` uncolored. The tone rules live only in `Report-Progress.ps1` (listed in `schema/deliver-profile.schema.json`, the deliver profile); the loop has no rules of its own. `.agents/deliver-loop.log` stays plain text. `-NoColor` or a non-empty `NO_COLOR` colors no stdout.
- Log pane (opt-in with `-LogPane`; herdr, `HERDR_ENV=1`, stdout a terminal): before the first iteration the loop splits a pane labeled `deliver-log` below the session (`herdr pane split --current --direction down --ratio 0.7 --no-focus`) that runs `pwsh -NoProfile -Command "Get-Content -Tail 40 -Wait <log>"` on the plain `.agents/deliver-loop.log`. A `deliver-log` pane already in the tab is reused, any herdr failure is ignored, the loop never closes the pane, so the last lines stay readable after the run. Without `-LogPane` no pane opens (the console already shows the colored lines); `-NoPane` is a deprecated no-op. The function is `Open-LogPane` in `scripts/TerminalBackend.ps1`. To see the log from another pane, a herdr key toggles it (`scripts/Switch-LogPane.ps1`, `references/terminal-backends.md` "Log pane toggle").
- Progress line after each step and each PBI (log and stdout): `M005 ▓▓▓▓░░░░ 7/19 · #322 review · 1 blocked · 1 needs you` (8 cells for closed/total; the PBI and step, blocked (waiting) and needs-you counts only when set).
- Notifications (macOS `osascript`, Windows toast, else none): from the `attention` events (`deliver.kind` `pr_opened`, `review_fix`, `ci_red`, `paused`, `blocked`) and `task.finished` `delivered` (merged) the harness writes, and the loop result. The urgency comes from the event's `tone`: on macOS `danger` plays a sound (Basso), `warning` another (Ping), the rest is silent.
- Terminal: the loop pushes no tokens and no agent state to herdr or poimen; the displays read the event file (ADR 0002, GravionLabs/agent-events). The token mapping the displays use is checked in as the token fixtures (`references/terminal-backends.md`). "Terminal" (colors, log pane) is `Test-LoopTerminal` in `scripts/TerminalBackend.ps1`: stdout not redirected, or `DELIVER_LOOP_ASSUME_TTY=1` (tests only). `Test-LoopAgentConflict` stays for callers that want to know whether another agent runs in the herdr pane. `-NoPane` prints a one-line deprecation warning.
- Progress events (ADR 0001, #452): the format is the agent-events core (GravionLabs/agent-events, pinned tag in `test/skills/delivery/agent-events/VERSION`): `SPEC.md`, `schema/v0/core.schema.json` (types `run.started`, `task.started`, `step.finished`, `progress`, `attention`, `attention.resolved`, `task.finished`, `run.finished`), plus the deliver profile `deliver@1` of this skill: `schema/deliver-profile.schema.json` (profile types `deliver.merging`, `deliver.release.updated`, `deliver.iteration`, fields under `deliver`, reason codes `deliver.<kind or outcome>` with the human sentence in `text`, tone rules). `scripts/Report-Progress.ps1 -Type <t> …` keeps the deliver CLI and maps it: `run.started` (`profiles`, `profileSchemas`, `agent`, `host` `poimen.terminal`, `herdr.pane`, `jsonl-file.pid`, `subject` the milestone or the one issue), `milestone.progress` → `progress` (`done`, `total`, `label: PBIs`), `issue.started` → `task.started` (`task: issue-<nr>`, `subject` `github.issue`), `step.finished` (`task`, `step`, the PR as link `rel: pull-request`), `attention`, `issue.finished` → `task.finished` (delivered → `succeeded`, blocked/paused/skipped → `skipped`), `release.updated` → `deliver.release.updated`, `iteration` → `deliver.iteration`. A task event for an issue without an open task starts it first; a later attempt is `issue-<nr>.<k>`. It appends the lines to `<git-common-dir>/.agents/events/<run>.jsonl` (`$AGENT_EVENTS_DIR/<run>.jsonl` when set). The run id is `AGENT_EVENTS_RUN`; `-Type run.started` without it creates one and prints `AGENT_EVENTS_RUN=<id>`, other types without a run do nothing. `seq` is gapless per run, `tone` and `needsYou` are decided by the script, the host comes from the environment. It never fails the caller. `SKILL.md` calls it for every step, attention and PBI end; the loop emits the rest:
- Run events of the loop: at the start `run.started` (`source: loop`, harness, model, repository, milestone key, title and URL) opens a new run (an `AGENT_EVENTS_RUN` of the calling shell is dropped). The loop exports `AGENT_EVENTS_RUN`, `AGENT_EVENTS_OWNER=1` (its own calls only) and `AGENT_EVENTS_DIR` (`<git-common-dir>/.agents/events/`, outside a repository `.agents/events/`) and passes the run to the harness with an empty `AGENT_EVENTS_OWNER` (nested). Per iteration `iteration` (n of max, the PBI) and `issue.started`; the steps (`step.finished`) and `attention` events (`pr_opened`, `review_fix`, `ci_red`, `paused`, `blocked`) come from the harness, which writes them nested into the loop's file; the loop follows the file (console, log, notifications); after each status read (`Get-DeliverStatus.ps1`, at the start and after each iteration) `milestone.progress` (`progress`) and the changes of its waiting items (`issue.finished` `blocked`), needs-you items (`attention` `needs_you`) and release round and PR (`release.updated`), an item that left the block reset with `issue.finished` `skipped`. After the iteration `issue.finished` from the GitHub state: closed `delivered`; `needs-decision` or `interactive` `paused`; `needs-refinement` or an open blocker `blocked`; else the `paused`/`blocked` attention event of the iteration, else `skipped`. At the end exactly one `run.finished` with the loop result; on an error or Ctrl+C the `finally` sends it with `no progress`.
- Control session (#517): it opens no run of its own, so the events directory holds one run file per delivery (`references/control.md`, Run).
- Nested sessions (#411, #463): `Report-Progress.ps1` writes no `run.started`/`run.finished` when `AGENT_EVENTS_RUN` is inherited (also with an equal `-Run`) and `AGENT_EVENTS_OWNER` is not `1`; nothing folds after `run.finished` (core rule).
- Run state: `scripts/ConvertFrom-ProgressEvents.ps1 -Path <run>.jsonl [-Now <iso>] [-NoPidCheck]` (or the lines on the pipeline) prints the fold of a run's events as JSON: the agent-events core run state (`schema/v0/run-state.schema.json`, it passes the core state fixtures of the pinned tag: `status`, `subject`, `progress`, open `tasks`, `finished`, `attentions`, `needsYou`, `links`, `gaps`) plus `deliver` (`schema/deliver-state.schema.json`: `result`, `milestone`, `iteration`, `delivered`, `blocked`, `paused`, `merging`, `needsYou`, `release`; the open RC test is a needs-you item `RC test` until the test issue finishes). Displays read the core only. Without `run.finished` the run is `running`, or `abandoned` when its `jsonl-file.pid` does not live or the last event is older than one hour. Unknown types (also the pre-core types of older files: `issue.started`, `milestone.progress`, …) and fields are ignored, an incomplete last line is skipped, a `seq` gap goes to `gaps`. Deliver profile fixtures: `test/skills/delivery/fixtures/progress-events/<case>.jsonl` with `<case>.state.json`, folded with `-Now '2026-11-07 12:00:00Z' -NoPidCheck`.
- Retention (ADR 0001): on `run.started`, `Report-Progress.ps1` (`scripts/ProgressRetention.ps1`) deletes event files `<events dir>/<run>.jsonl` and run directories `.agents/deliver-loop/<run>/` of finished and abandoned runs older than `AGENT_EVENTS_KEEP_DAYS` (default 7, by last write time) and keeps at most the newest `AGENT_EVENTS_KEEP` (default 100) runs per location. A run is abandoned when it has no `run.finished` and its writer pid (`jsonl-file.pid`) does not live or its file has not changed for one hour. Running runs (live pid) and the current run are never deleted; a failed delete is skipped silently.

## Reading a run

An agent with a shell reads runs through `scripts/Get-RunState.ps1` instead of locating and parsing the event files itself (read-only; the events directory is resolved as in `Report-Progress.ps1`: `AGENT_EVENTS_DIR`, else the git common dir):

```powershell
pwsh <skill-dir>/scripts/Get-RunState.ps1 -List
pwsh <skill-dir>/scripts/Get-RunState.ps1 -Run <run>
pwsh <skill-dir>/scripts/Get-RunState.ps1 -Run <run> -After <seq>
pwsh <skill-dir>/scripts/Get-RunState.ps1 -NeedsAttention
```

`-List` prints the runs newest first (`run`, `startedAt`, `result`, `lastType`, `lastTs`); `-Run` prints the fold (core run state plus `deliver`, the same reducer as above); `-Run … -After <seq>` prints the newer events, one JSON line each, for polling; `-NeedsAttention` lists the open needs-you items (`deliver.needsYou`) of the running runs. An unknown run exits 1 with one line on stderr; no events directory is an empty list.
