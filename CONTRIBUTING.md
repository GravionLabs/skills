# Contributing to GravionLabs/skills

Thanks for contributing. GravionLabs/skills is a library of reusable **skills**, installed with `npx skills` and usable from Claude Code, OpenCode and GitHub Copilot. [AGENTS.md](AGENTS.md) describes the layout, groups and conventions; this file covers the contribution workflow.

## What belongs here

- Skills that encode a **repo or team convention**, a **tool contract** (schema, CLI flags, non-obvious gotchas), or a **repeatable procedure** (script + templates).
- Fixes to existing skills: contradictions, stale commands, duplicated rules.

What does not belong here:

- Generic best practices the model already knows (tool basics, language tutorials, flag tables).
- Secrets, internal URLs, project-specific identifiers.
- Agents, hooks, prompts or a pipeline of its own. Workflows are skills; delivery is the `deliver` skill.

## Setup

```powershell
pnpm install
pwsh skills/shared/check-prerequisites/scripts/Check-Prerequisites.ps1 -Full
```

The repo uses pnpm (`pnpm-lock.yaml`) only.

## Adding or changing a skill

1. Put it under `skills/<group>/<name>/` (the folder is the group; names are unique across groups, installs are flat by name). Use the `skill-write` skill or start from its `assets/skill-template-optimized.md`.
2. Keep `SKILL.md` ≤ 100 lines; frontmatter only `name`, `description`, optional `license`/`metadata` plus the client keys of [skill frontmatter](docs/concepts/skill-frontmatter.md); shell fences ` ```powershell `. Long specs go to `references/` with a conditional load line, templates to `templates/`, procedures to `scripts/*.ps1`.
3. If another skill already owns a step, delegate by name instead of repeating it.
4. List it and run the checks:

   ```powershell
   node scripts/check-marketplace.mjs --fix   # marketplace.json and groups.json from the folders
   pnpm run check                                                  # everything CI runs
   ```

   Tests of skill content and scripts live in `test/skills/<group>/`, repository checks in `test/repo/`, shared helpers in `test/helpers/`. `pnpm test` runs Vitest, `pnpm run test:ci` adds coverage (CI), a single file runs with `pnpm vitest run <path>`.
5. Update the group `description` in `.claude-plugin/marketplace.json` when the group scope changed, and the group table in AGENTS.md and README.md.
6. Open a PR with a conventional-commit title (`feat(py): …`, `fix(github): …`). The changelog is generated from commit messages with git-cliff.

   Every PR closes an issue (`Closes #n` in the body), also docs, roadmap and sync PRs; only release PRs from `release/**` are exempt. The required check `PR checks` (`.github/workflows/pr-checks.yml`, readiness job of GravionLabs/ci) fails a PR that closes no issue or closes one labelled `needs-decision` or `needs-refinement` or blocked by an open issue. Open an issue first when there is none.

## Dogfooding: project skills

Project skills take precedence over global ones. Without them, a `deliver` run in this repository loads the global copy (`~/.claude/skills/deliver`) instead of `skills/delivery/deliver/`. Link the repository skills as project skills before `deliver` runs here:

```powershell
pwsh scripts/Link-Skills.ps1           # links skills/<group>/<name> to .claude/skills/<name> and .agents/skills/<name>
pwsh scripts/Link-Skills.ps1 -Remove   # removes only these links
```

Both folders are gitignored. An existing link is replaced; a real directory of the same name stays and is reported.

## Generated files

`docs/skill-list.md` is generated by `pnpm run generate` from `.claude-plugin/marketplace.json` and the skill descriptions. It is gitignored; CI and the Pages workflow generate it in the working tree for the site build.

## Docs site

`site/` is a VitePress site that renders `docs/` in place; the home page is the hero and feature landing page `docs/index.md`; the root `README.md` is the GitHub landing page only. Preview it with `pnpm --filter site dev`. A local build needs the generated list first: `pnpm run generate`, then `pnpm --filter site build`. A PR touching `site/**`, `docs/**`, `skills/**` or `README.md` runs the "Build the site" check (`.github/workflows/pages.yml`). Only `main` deploys, and only while the repository variable `DEPLOY_PAGES` is `true`; the site is at <https://gravionlabs.github.io/skills/>. Details in `site/README.md`.

## Public surface and renames

Public surface is everything a consumer can depend on: skill names (`npx skills add --skill <name>` and `skills-lock.json` record them), group names (`/skills-manage <group>`), script parameters and entry points.

- Announce every rename in the PR body and in the release notes.
- A renamed skill leaves a `skills-lock.json` entry behind in every consumer: `npx skills update` cannot follow a rename. Prefer keeping names; when a rename is unavoidable, batch it into a major release and describe the `npx skills remove <old>` / `add <new>` step in the release notes.
- Batch breaking renames into one major release (empty `+semver: major` commit, see Releases). Only that dedicated empty release commit carries `+semver: major`; no other commit does, and none uses `<type>!:` or `BREAKING CHANGE:` (both bump major too).

Renamed when moving from GravionLabs/apm-hub:

| Old name                      | New name                   | Note                                        |
| :---------------------------- | :------------------------- | :------------------------------------------ |
| `apm-install` (skill)         | `skills-manage`            | installs with `npx skills` instead of `apm` |
| `apm-tooling` (package)       | `skill-tooling` (group)    | same skills                                 |
| `core`, `all` (meta-packages) | presets of `skills-manage` | no longer installable units                 |

Renamed since:

| Old name               | New name        | Note                                                                          |
| :--------------------- | :-------------- | :---------------------------------------------------------------------------- |
| `ng-ag-grid-developer` | `ng-ag-grid`    | same skill; `npx skills remove ng-ag-grid-developer`, then `add` `ng-ag-grid` |

## Issues

Use the templates in `.github/ISSUE_TEMPLATE/` (Epic → Feature → PBI, Bug; there is no Task level). Children are linked as native GitHub sub-issues; see `skills/github/github-issue/references/sub-issues.md`.

The title of an issue starts with its level: `[Epic]`, `[Feature]`, `[PBI]` or `[Bug]`, then the summary (`[PBI] feat: short summary`). The shared `issues.yml` workflow of `GravionLabs/ci` sets the prefix from the level label.

## Releases

Releases are cut from a single rolling branch, `release/next`. The version bump comes from the Conventional Commits on the branch: `fix:` → patch, `feat:` → minor, `<type>!:` or `BREAKING CHANGE:` → major; a release with only fixes is a patch release. `github-release finish` adds no bump commit. The release PR into `main` is merged with a merge commit, never squashed, so the `feat:`/`fix:` commits stay visible to GitVersion and git-cliff. A release is a git tag; consumers pin it with `npx skills add GravionLabs/skills#v<x.y.z>` or `skills-manage -Ref v<x.y.z>`.

- Major on purpose: `github-release finish major` adds an empty commit with `+semver: major` in its message. Renames ship here, see [Public surface and renames](#public-surface-and-renames).
- Hotfix: fix on `main` (merge commit, the `main` ruleset allows only merge), then merge `main` into `release/next`.
- Parallel lines: use `release/<x.y>` branches.

Details: `skills/github/github-issue/references/release-branches.md`.
